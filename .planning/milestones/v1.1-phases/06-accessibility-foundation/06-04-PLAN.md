  <action>
Read `Toast.tsx` fully to understand the current structure — particularly the `ToastProvider` render method and how toasts are rendered in the container.

Modify the Toast container to use TWO separate always-mounted aria-live regions instead of one:

1. Keep the outer `role="region"` `aria-label="Notifications"` container.
2. Inside it, create two child divs:
   - **Polite region**: `aria-live="polite"` `aria-atomic="false"` — renders toasts where `variant` is NOT `"error"` or `"warning"` (i.e., info, success, or default/undefined)
   - **Assertive region**: `aria-live="assertive"` `aria-atomic="true"` — renders toasts where `variant` IS `"error"` or `"warning"`

Both regions must ALWAYS be in the DOM (not conditionally rendered). When empty, they render no children but the div remains. This is critical — screen readers register live regions on mount; adding them dynamically misses the first announcement.

Filter the toasts array into two lists based on variant. Render each list in its respective region. Preserve existing toast animation, styling, and dismiss behavior.

Do NOT change:
- Toast item component structure or styling
- Toast dismiss/timeout behavior
- The toast hook API (useToast)
- Any toast variant styling (colors, icons)

Run tests to confirm existing Toast tests pass and the new structure doesn't break axe assertions.

**Progress.tsx and Spinner:**
Read `Progress.tsx` (which also exports `Spinner`). Add a visually-hidden `aria-live="polite"` status region to both Progress and Spinner:

```typescript
<span
  role="status"
  aria-live="polite"
  aria-atomic="true"
  className={styles.srOnly}  // or inline style
  // Visually hidden but accessible: position absolute, width/height 1px, overflow hidden, clip rect(0,0,0,0)
>
  {/* Text content changes trigger announcement */}
</span>
```

For Spinner: The region says "Loading" when the spinner is visible. Since Spinner is always visible when rendered (it doesn't have an on/off state — you render it when loading), the live region should contain "Loading" text. When the parent removes the Spinner, the region disappears too — but the completion announcement ("Content loaded") should be handled by the parent, not the Spinner (since Spinner is unmounted at that point). Actually, per CONTEXT.md: "announce 'Loading...' on start and 'Content loaded' on completion". Since Spinner gets unmounted on completion, we can't announce "Content loaded" from within Spinner. Instead: add an `aria-label` prop (Spinner already has a `label` prop per existing test). Ensure the existing `label` prop is used as the accessible name. Add `role="status"` and `aria-live="polite"` to the Spinner wrapper if not already present.

For Progress: The progress bar already has `aria-label`. Add `role="progressbar"` if not present, plus `aria-valuenow`, `aria-valuemin="0"`, `aria-valuemax="100"`. Add a visually-hidden live region that announces current progress at key thresholds (or just announce the percentage). Actually, `role="progressbar"` with `aria-valuenow` is the standard — screen readers announce progress natively. Just ensure these ARIA attributes are present.

**Skeleton.tsx:**
Read `Skeleton.tsx`. Add `aria-hidden="true"` to the outermost element. Skeleton is a visual-only placeholder — screen readers should skip it entirely. Per CONTEXT.md: "Skeleton components don't announce (visual-only)."

**Alert.tsx:**
Read `Alert.tsx`. Per research, Alert already uses `role="alert"` for error/warning and `role="status"` for info/success. Verify this is correct. Per CONTEXT.md: "only dynamic alerts (appearing after user action) get `aria-live`; static/on-load alerts are found naturally by screen readers."

The `role="alert"` already implies `aria-live="assertive"` and `role="status"` implies `aria-live="polite"` — so Alert does NOT need explicit `aria-live` attributes IF the roles are correctly set. Verify the roles are correct. If Alert is missing roles, add them per the variant:
- `error` / `warning` variants: `role="alert"`
- `info` / `success` variants: `role="status"`

Do NOT add `aria-live` explicitly to Alert — the implicit live semantics from `role` are sufficient and per CONTEXT.md, only dynamic alerts should announce. The `role` handles this correctly.

Run full test suite to verify no regressions.
