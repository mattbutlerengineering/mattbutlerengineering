# Roadmap: Milestone v1.3 - AI Developer Velocity

**Milestone Goal:** Dramatically reduce latency in the Research and Execution phases by optimizing monorepo tooling and providing high-density context for AI agents.

## Phases

### Phase 19: Turbo Remote Caching
**Goal**: Enable Turbo remote caching to prevent redundant builds and type-checks across local and CI environments.
**Success Criteria**:
  1. `turbo build` and `turbo typecheck` report cache hits on subsequent runs without code changes.
  2. Remote cache is configured (e.g., via Vercel or a custom server) and authenticated.
  3. CI pipeline logs show `[remote cache hit]` for unchanged packages.

### Phase 20: Pre-commit Hook Optimization
**Goal**: Reduce the "Wait Time" during commits by moving heavy global checks to CI and parallelizing remaining local checks.
**Success Criteria**:
  1. Pre-commit hooks complete in < 5 seconds for single-file changes.
  2. Global checks (circular dependencies, service bindings) are moved to `pr-quality-check.yml`.
  3. `lint-staged` configuration is optimized to run only necessary per-file tasks.

### Phase 21: Gemini Intelligence Context (GEMINI.md)
**Goal**: Create a high-density `GEMINI.md` file that provides immediate architectural and operational context to reduce the need for expensive recursive searches.
**Success Criteria**:
  1. `GEMINI.md` exists in the root with sections for: Core Architecture, Critical Selectors (e.g., #main-content), Common Commands, and Anti-patterns.
  2. The file is registered in `CLAUDE.md` or as a system prompt mandate.
  3. AI agent Research phase for a new task is reduced by at least 2 turns on average.

### Phase 22: Service-Level LLM Context
**Goal**: Generate and maintain service-specific `llms.txt` files for `users`, `reservations`, and `agent` services to expose API surface area directly to agents.
**Success Criteria**:
  1. Each service directory contains an `llms.txt` listing its endpoints, Zod input/output schemas, and authentication requirements.
  2. A script in `tools/cli` automatically updates these files by parsing Prisma models and Hono/Express routes.
  3. Agents can resolve service-specific integration tasks using only the service's `llms.txt`.

### Phase 23: Standardized Agent Error Schema (RFC 7807)
**Goal**: Implement RFC 7807 (Problem Details for HTTP APIs) across all backend services to provide machine-readable error context.
**Success Criteria**:
  1. All services return `Content-Type: application/problem+json` for error responses (4xx/5xx).
  2. Error bodies include `type`, `title`, `status`, and `detail` fields as per the spec.
  3. Agents can accurately diagnose and suggest fixes for API failures based on the machine-readable error details.

### Phase 24: Unified "mbe up" Bootstrapping
**Goal**: Create a single CLI command (`mbe up`) that orchestrates Docker, environment initialization, database migrations, and development servers.
**Success Criteria**:
  1. A new `up` command is added to the `mbe` CLI tool.
  2. The command handles dependency checks (Docker, pnpm), starts the database, runs `prisma db push`, seeds data, and starts the Turbo dev server.
  3. A fresh developer/agent environment can go from "clone" to "ready" in one command.

### Phase 25: Architecture Decision Records (ADR)
**Goal**: Establish a formal ADR process to document the "why" behind technical choices, preventing agents from re-litigating settled architectural decisions.
**Success Criteria**:
  1. `docs/adr/` directory exists with an initial set of records (e.g., ADR-01: Rialto over Tailwind).
  2. ADRs follow a standard template (Context, Decision, Consequences).
  3. Agents reference ADRs when proposing structural changes.

### Phase 26: Automated AI Regression Testing
**Goal**: Implement CI validation for the Generative UI pipeline to ensure Rialto updates do not break AI code generation.
**Success Criteria**:
  1. A CI job in `agent-task.yml` triggers a sample UI generation from a fixed prompt.
  2. The generated output is validated for structural correctness (valid Rialto components) and visual regression (Playwright/axe-core).
  3. Failures in Rialto component updates are caught if they prevent the LLM from generating working code.

### Phase 27: Custom ESLint AST Rules
**Goal**: Enforce project-specific architectural patterns (e.g., no Tailwind, RFC 7807 for errors) via automated AST linting.
**Success Criteria**:
  1. `eslint-plugin-local-rules` is configured in the monorepo.
  2. At least two custom rules are active (e.g., `no-tailwind-classes`, `require-rfc-7807-errors`).
  3. `pnpm lint` catches violations of these rules in CI.

### Phase 28: Strict Internal Zod Schema Enforcement
**Goal**: Ensure every internal service boundary is strongly typed and validated at runtime to prevent hallucinated payloads.
**Success Criteria**:
  1. All cross-service HTTP calls use Zod to validate responses before returning.
  2. A new CI job runs API contract tests between services to detect drift.
  3. A common `@mbe/service-schemas` package or similar mechanism is used to share types.

### Phase 29: Agent Success Rate Tracking
**Goal**: Establish a baseline metric for AI agent autonomous task completion to measure the impact of Developer Velocity improvements.
**Success Criteria**:
  1. A lightweight mechanism (e.g., a markdown log or simple DB table) is created to log agent sessions.
  2. Sessions track the task, time spent, turn count, and success/failure/human intervention.
  3. A CLI command or script aggregates this data to report a "Success Rate."

### Phase 30: CI Performance & Bundle Size Budgets
**Goal**: Prevent new features or AI-generated code from degrading UX by enforcing strict performance budgets in CI.
**Success Criteria**:
  1. `size-limit` is configured for all critical web apps, not just the Rialto package.
  2. Lighthouse CI is configured to block PRs if performance scores drop below defined thresholds.
  3. AI-generated code that blows the budget fails CI automatically.

### Phase 31: "Golden Path" CLI Generators
**Goal**: Reduce boilerplate and ensure new code perfectly matches the architecture by building code generators into the `mbe` CLI.
**Success Criteria**:
  1. `mbe new component` scaffolds a Rialto component with tests, showcase entry, and updates `llms.txt`.
  2. `mbe new route` scaffolds an API endpoint with RFC 7807 error handling and Zod validation.
  3. Generated code passes all linters and tests immediately.
