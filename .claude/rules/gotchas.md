# Known gotchas

Project-specific traps that have bitten me before. Read these before diving into pre-commit, release, or deploy work.

> **Adding entries:** after an autonomous loop (`/implement-queue`, `/ship-loop`), run `/gotcha-harvest` to mine the session for `CI failed → fix → passed` arcs and recurring tool-errors — it proposes new bullets here (and cross-repo facts to memory) with human review. `/reflect` only captures _human corrections_, so loop-discovered gotchas land here via `/gotcha-harvest`, not `/reflect`.

## Pre-commit / lint

- **There is no `$CLAUDE_FILE_PATH` — hooks get the edited path as JSON on stdin (fixed in #3631).** Measured against the installed binary (v2.1.220): the string `CLAUDE_FILE_PATH` does not occur in it at all, and the only hook-injected env var is `CLAUDE_PROJECT_DIR`. The path arrives on **stdin** as `{"hook_event_name":…,"tool_name":"Write","tool_input":{"file_path":"/abs/path"},"tool_use_id":…}`. Seven hooks in `.claude/settings.json` used to interpolate the nonexistent variable, which expanded to `""` — so `prettier --write ""` recursively reformatted the **entire working directory** (168 tracked files, silenced by `2>/dev/null`) and `case "" in *.env|*pnpm-lock.yaml|…)` matched nothing, leaving the `.env`/lockfile/migration/`Pulumi.prod.yaml` guard inert for its whole life. Every path-aware hook now starts with `FILE=$(node "$CLAUDE_PROJECT_DIR/.claude/hooks/hook-input.mjs"); [ -n "$FILE" ] || exit 0;`. **Never pass an unguarded variable to a formatter** — an empty argument means "everything" to `prettier`, `eslint`, and most CLI tools, so the `-n` guard stays even now that the path resolves. `settings.json` is strict JSON (no comments), so the contract is documented in `scripts/hook-input.mjs` — the one module that owns "how does a hook obtain its input" — and enforced by `scripts/__tests__/hook-input.test.mjs`, which executes every real hook command in a sandbox. `CLAUDE_BASH_COMMAND`, `CLAUDE_TOOL_INPUT` and `CLAUDE_TOOL_OUTPUT` are **also** absent from the binary. `pre-bash-guard.sh`, `pre-push-typecheck.sh` and `verify-push-sha.sh` were inert on `$CLAUDE_BASH_COMMAND` for the same reason until they adopted the adapter (`hook-input.mjs command` → `extractHookField(payload, "command")`); seam tests in `scripts/__tests__/hook-input.test.mjs` now exercise all three for real and fail if any hook file reads the dead vars again. `regen-after-update-branch.sh` is the one hook deliberately left inert (allowlisted in that test, seeded in `docs/backlog.md`) — **review its lines 36-58 before repairing its input**: it runs `git checkout origin/$branch --detach` and `git push --no-verify` in the live working tree and has never once executed.
- **PreToolUse secret-scan hook (`.claude/hooks/secret-scan.mjs`)** shifts the CI Gitleaks scan left to edit time: on `Edit|Write|MultiEdit` it scans the content an agent is about to write for high-confidence secrets (Stripe `sk_live_`/`pk_live_`/`rk_live_`, AWS `AKIA`/`ASIA` key ids, JWTs, PEM private-key headers) and **blocks the write (`exit 2`)** on a hit, before the secret ever reaches a commit. Detection is the pure, unit-tested `scanForSecrets()` in `scripts/secret-scan.mjs` (test-mode keys, `.example`/`.sample`, `__tests__`/`fixtures`, and `.md` are allowlisted to keep false positives near zero); the hook fails **open** (`exit 0` on any parse error) so a hook bug never deadlocks editing. The hook is wired in `.claude/settings.json` under `PreToolUse`.
- Commit hooks: pre-commit runs `eslint --fix` + `check-adr`; post-commit runs `pack-changed` (regenerates `llms.txt` / `llms-full.txt` in affected packages — expect them to appear in `git status` after your commit lands)
- JSX strings with `'` fail `react/no-unescaped-entities` at commit time — use `&apos;`
- **Rialto components must NOT call `setState` inside a `useEffect` body** (pre-commit hook bans it in `packages/rialto`). Setting state re-renders → re-runs the effect → sets state again = render loop. Use render-time derivation (compute during render, the snapshot pattern) or event handlers (set state only on user actions). LLMs default to the forbidden useEffect+setState sync pattern from general React tutorials — it's a correctness bug in Rialto's rendering model
- **lint-staged passes generated files to ESLint as explicit CLI args** — ESLint 10's `ignores` array in config only applies to glob-resolved files, not explicit paths. When lint-staged stages a Prisma generated file (`services/*/src/generated/**`), it passes the path directly to `eslint`, bypassing the ignore. `lint-staged.config.js` filters `/generated/` paths before grouping to prevent this

## Pre-push / typecheck

- **Vitest does NOT typecheck** — tests can pass with completely wrong types. If you add test mocks, they must match the actual interface shape (e.g. `SessionResult` needs `status`/`sessionId`/`branchName`, not `success`/`stuck`/`outputs`). **Nothing catches this before push:** this bullet used to end "Pre-push hook now runs `turbo typecheck` before `turbo test`", and that has been false since #2811 (`perf(hooks): scope pre-commit semgrep to staged files and drop pre-push affected-test gate`) deliberately removed the gate. `.husky/pre-push` runs exactly four things — the destructive-migration check, the AI-antipattern ratchet, a gated CLI build + `pnpm regen`, and `pnpm regen --check` — no typecheck and no tests. A stale claim like this is worse than no claim: it reads as a safety net, so a wrong-typed mock gets pushed on the belief that a green push means a green typecheck, and CI is the first thing that actually disagrees. Run `pnpm typecheck` yourself before pushing (or `pnpm turbo typecheck --filter='...[HEAD]'` for just the affected packages), and treat CI — not the hook — as the gate.
- **Worktree agents must run `pnpm typecheck` before declaring done.** Agents that only run `pnpm test` will miss type errors that break CI. This is the #2 recurring CI failure pattern after the missing `pnpm install` pattern

## Build / pnpm / turbo

- Run `pnpm` from inside a package directory, not the monorepo root — turbo filter errors out at the root for `test`/`typecheck`/`build` in most packages
- Parallel `Bash` tool calls don't share `cd` state and race each other — use absolute paths or `pnpm --dir <abs-path> <cmd>` when running in parallel
- **Worktree agents must `pnpm install --frozen-lockfile` before running tests/builds.** Claude Code `isolation: "worktree"` creates a bare checkout without `node_modules`. Without the install step, `vitest: command not found` / `ELIFECYCLE` failures are guaranteed. This is the #1 recurring CI failure pattern across agent sessions. The `implement-queue-worker` subagent ([CLAUDE.md § Subagents](../../CLAUDE.md#subagents)) runs this step automatically as step 0 of its protocol.
- **`gh pr update-branch` drifts llms.txt artifacts** — the merge brings in new main changes but doesn't re-run `pnpm regen`. CI's "Verify generated artifacts" step then fails on stale llms.txt/llms-full.txt. The `regen-after-update-branch.sh` PostToolUse hook auto-fixes this by building the CLI (`pnpm build --filter @mbe/cli...`), running `pnpm regen`, and pushing a fixup commit. If the hook is unavailable, run manually: `pnpm build --filter @mbe/cli... && pnpm regen`, then commit and push
- **llms-drift treadmill (fixed in #2745)** — three root causes caused every worktree-PR to need a manual regen cycle: (1) `@mbe/agent-core/dist` is absent in fresh worktrees → `mbe pack` fails with `ERR_MODULE_NOT_FOUND` → llms NOT rebuilt; (2) `regen.mjs` ran `llms-txt` BEFORE `rialto-catalog-schemas` → llms embedded the pre-regen schema while CI regenerated with the post-regen schema; (3) the update-branch hook didn't build the CLI before regen → hook was a no-op. All three are now fixed: pre-push builds CLI first, `regen.mjs` runs llms-txt last, and the update-branch hook also builds CLI. Residual caveat: if `pnpm build --filter @mbe/cli...` fails (e.g. TS error introduced by the PR), the pre-push hook aborts before regen — fix the build error first. This whole class is what the `generated-artifact-determinism-reviewer` subagent ([CLAUDE.md § Subagents](../../CLAUDE.md#subagents)) exists to catch at edit time, before it wedges a merge train the way it did across #2195→#2217.
- **llms regen also requires `packages/agent-core` built, and the PostToolUse hook fails open on it** — `mbe pack <pkgDir>` (the `@mbe/cli` command the llms-txt family's `changedBy()` shells out to) imports `@mbe/agent-core`, so a maximally-fresh worktree missing `packages/agent-core/dist` throws `ERR_MODULE_NOT_FOUND`, not just a missing CLI build. `regen-llms.sh` runs that command with `"${cmd_arr[@]}" >/dev/null 2>&1 || continue` — the failure is silently swallowed (no warning printed, loop just moves to the next family), so the hook no-ops with zero signal. Always `pnpm build --filter @mbe/cli...` (which builds `agent-core` as a transitive dep) before relying on the hook or running `mbe pack`/`pnpm regen` by hand
- **A _stale_ `packages/agent-core/dist` silently narrows `/implement-queue`'s review gate — a distinct failure mode from the missing-dist entry above (#3989).** The missing-dist gotcha fails LOUDLY: `ERR_MODULE_NOT_FOUND` the instant `isLowRiskPR`/`reviewersForDiff` (or anything shelling through `mbe pack`) tries to import a dist that was never built. This one fails SILENTLY: the dist exists, imports fine, and returns confident, wrong answers, because `dist/` is gitignored and nothing rebuilds it before Phase 2 reads it — whatever the last build in that checkout produced, however old, is what a session gets. Observed on PR #3988: `apps/rialto-web/e2e/demo-nav.spec.ts` changed — exactly what `e2e-selector-drift-reviewer` exists to catch — but `reviewersForDiff([...])` returned `[]` from a dist that predated the mapping (present in `pr-risk-classifier.ts` at the time) by 77 minutes. No error, no log line, `git status` clean (dist is gitignored) — the gap was only found by manually rebuilding and re-running the same call. The dangerous direction is narrowing: fewer specialists dispatched, more PRs read as low-risk, never the reverse, so it's silent by construction — a false "safe" reads exactly like a genuinely safe PR. Fixed by `scripts/agent-core-build-freshness.mjs`: `classifyBuildFreshness()` is a pure decision (newest `src/**` mtime vs. newest `dist/**` mtime) that fails closed on `stale`, `missing`, AND `unknown` (undeterminable src mtime — never trust an existing dist just because staleness couldn't be proven); `ensureFreshAgentCoreBuild()` is the thin wrapper that rebuilds once and re-checks, never throwing. `.claude/skills/implement-queue/SKILL.md` Phase 2 step 2 now runs `node scripts/agent-core-build-freshness.mjs check` before the first classifier call each iteration — exit 1 means treat the PR as needing full review, never as low-risk or specialist-free.
- **FIXED (#3911): `infrastructure/worker` used to not be a pnpm workspace package — it now is.** `pnpm-workspace.yaml` lists `"infrastructure/worker"` explicitly, `infrastructure/worker/package.json` (`@mbe/edge-worker`, `type: module`) declares real `lint`/`test`/`test:coverage` scripts, and `infrastructure/worker/vitest.config.mjs` is picked up by the root `vitest.config.ts`'s `infrastructure/*/vitest.config.*` glob. Its 15 `*.test.js` files (edge-router, health, rate-limiter, csp, etc. — 245 tests) run under `pnpm test`/`turbo test` and are part of `CI Gate` (the `test` job is one of `ci-gate`'s `needs`); coverage is uploaded via `./infrastructure/worker/coverage/coverage-final.json` in `ci.yml`. `scripts/check-orphaned-tests.mjs` (wired into `repo-audit`) now guards against this class recurring — any test file outside a workspace package's declared `test` script fails the check unless allowlisted. No more manual `pnpm exec vitest run infrastructure/worker/` workaround needed — `pnpm test` covers it.
- **A workflow that invokes Playwright directly (not through a package script) can silently scope itself to one spec forever, even though `apps/*/e2e/` holds several (#3955)** — `rialto-web-visual.yml` (now `rialto-web-e2e.yml`) called `playwright test … apps/rialto-web/e2e/visual.spec.ts` by explicit path, and its own header comment said so — but nothing else in the repo ever invoked the other six specs (`a11y-pages`, `interaction`, `navigation`, `search`, `theme`, `demo-nav`). They read as covered on inspection (real `expect()` assertions, checked in, sitting right next to visual.spec.ts) which is worse than absent, because a passing-looking spec that never runs pins nothing — the regression it guards against (#3939/#3954) can return with no check going red. Same mechanism class as the (now-fixed) `infrastructure/worker` entry above (a real test, invisible to CI), different trigger: workspace non-membership there, hand-written workflow scoping here. Fix pattern: `rialto-web-e2e.yml` now runs the functional specs in their own job with an **explicit** file list (never a glob — a glob fails silently in the opposite direction, quietly picking up or dropping files), and `apps/rialto-web/e2e/workflow-coverage.test.ts` (run by `pnpm --dir apps/rialto-web test`) fails if any `e2e/*.spec.ts` file isn't referenced by full path in the workflow, so a new spec added without wiring it in breaks the gate instead of silently never running.
- **`pnpm exec mbe <cmd>` fails with `Command "mbe" not found`** — the `@mbe/cli` bin (`tools/cli/package.json`'s `bin.mbe`) is never linked into any `node_modules/.bin`: pnpm only symlinks a workspace package's bin into consumers that declare it as a `dependency`, and nothing in the workspace depends on `@mbe/cli`, so `pnpm exec` fails even run from inside `tools/cli` itself. After `pnpm build --filter @mbe/cli...`, invoke `node tools/cli/dist/index.js <cmd>` or `pnpm --filter @mbe/cli start <cmd>` instead. `claude.yml`'s `pnpm exec mbe agent run` step shares this bug.
- **Agent worktrees leak permanently once a worker commits (fixed in #3950)** — Claude Code's `isolation: "worktree"` only auto-removes a worktree that is _unchanged_; every successful worker commits, so its worktree is never auto-removed, and nothing in `/implement-queue` reclaimed it either. This let `.claude/worktrees/` grow to 132 (129 stale, none with an open PR) six days after a 128→66 manual sweep. Fixed by `scripts/reap-worktrees.mjs` — a pure `decideWorktreeReap` safety gate (refuses any worktree with an open PR or a live owning process, the latter derived from the OS process table via `lsof -t +D`, not a PID file — no lock file is ever written per worktree) wired into `/implement-queue` Phase 4. Deliberately ignores working-tree dirtiness (the PostToolUse prettier hook keeps every worktree permanently "dirty") and git ancestry (PRs squash-merge, so a worker branch's tip is never literally an ancestor of `main`) — neither is a real safety signal, so removal always uses `git worktree remove --force`.
- **Turbo silently shares its local filesystem cache across git worktrees of this repo (fixed in #3786)** — turbo 2.10.8 ships built-in git-worktree detection (`turborepo-scm::worktree::detect`). Without an explicit `cacheDir` in `turbo.json`, turbo resolves the local cache to whichever worktree it considers "main" instead of the current one, so a linked `implement-queue-worker` worktree can get a "cache hit" for a task it never ran, silently replaying build output (and logs) produced by a _different_ worktree. This caused a real incident (#3593): a concurrent worktree build raced the main checkout's `pnpm build --filter @mbe/cli...`, and the main checkout served a stale `packages/agent-core/dist/index.js` missing an export that existed in source, breaking the pre-commit hook with `SyntaxError: ... does not provide an export named 'suiteDidNotRun'` — no build error, just plausible-looking wrong output. Fix: `turbo.json` now declares `"cacheDir": ".turbo/cache"` explicitly, which makes every checkout (main or any worktree) resolve to its own local cache directory instead of turbo's auto-detected shared one. Reproduce/verify with `scripts/repro-turbo-worktree-cache.sh` (builds a target in this checkout, then in a fresh worktree with no `node_modules`, and asserts the second build cache-misses instead of replaying the first's output).

## CI

- **GH Actions is paid and runs on every PR** — verify state with `gh run list --limit 5` before claiming CI is broken
- **Green-main policy: main must always be green.** No admin-merge through red checks. If main breaks, fix is top priority. Emergency revert is the only exception
- **`CI Gate` is the only _required_ status check on `main`.** `codecov/patch` (patch-coverage delta) and `Hospitality E2E` (auth/booking-widget specs, frequently red for environmental/auth-bypass reasons) are advisory — not required. Gate merge decisions on `CI Gate` + the build/test/lint/typecheck/Integrity/Architecture-Audit jobs, not on an all-green rollup. Verify required contexts with `gh api repos/.../branches/main/protection/required_status_checks`. **`main` is NOT `strict`** — measured 2026-08-17, that endpoint returns `{"strict": false, "contexts": ["CI Gate"]}`. This entry said the opposite for months, and the false claim was load-bearing: it is the stated reason for the update-branch churn in the auto-merge bullet below, for `automation-pr-rescue.yml` existing at all, and for the N² merge-train tax that #3389 was filed to solve. A `BEHIND` PR is mergeable here. Re-measure before building anything on top of either answer — branch protection is repo state, not repo code, so nothing in this tree changes when it flips and no diff records that it did
- **Auto-merge, not merge queue (personal-account repo).** GitHub's native merge queue (`merge_queue` ruleset rule, the dormant `merge_group:` trigger in `ci.yml`) is unavailable on this repo — creating the ruleset returns `422 Invalid rule 'merge_queue'`. Re-probed 2026-08-17, and the first error you get is misleading: with the default merge method the API answers `Invalid rule 'merge_queue': Invalid merge method 'merge'. Not allowed for this repository.`, which reads like a fixable parameter problem. Supplying `merge_method: "SQUASH"` (the only method this repo allows) and a full valid parameter set gets `Invalid rule 'merge_queue': ` — a refusal with an **empty** reason, i.e. the parameters validated and the rule was still rejected. Don't stop at the first 422 and conclude the parameters are wrong. The implement-queue merge train uses **auto-merge** instead: `gh pr merge <N> --auto --squash --delete-branch` (repo has `allow_auto_merge: true`). `--auto` enqueues the merge; GitHub completes it once `CI Gate` is green **and** the branch is up to date — it does **not** auto-rebase. Whether a PR that falls behind still auto-merges depends on branch protection's `strict` flag, which is **currently off** (see the bullet above) — so a `BEHIND` PR should merge without an `update-branch`. Much of the tooling below was built when it was on; treat that machinery as belt-and-braces rather than load-bearing, and re-measure `strict` before concluding a stuck PR is stuck for this reason. To dequeue, `gh pr merge <N> --disable-auto`. Run the diff-matched review gate **before** setting `--auto` — once enqueued, GitHub merges on green with no further human gate. The `reviewer` subagent ([CLAUDE.md § Subagents](../../CLAUDE.md#subagents)) is that gate
- **GitHub Actions' default shell does NOT set `pipefail` — a gate command piped into `tee`/`head`/`grep` reports the pipe's exit code, so the step goes green no matter what the gate found.** Measured, not assumed: the runner log for a `run:` block prints `shell: /usr/bin/bash -e {0}` — `-e` only, no `-o pipefail`. So `node some-check.mjs | tee out.log` exits with `tee`'s status (always 0) and a failing check silently passes. This is the same shape as the `git push | tail` trap already recorded in memory, and it is worse in a workflow because the green step is the only thing anyone looks at. Caught during #4505 while building `scripts/check-api-surface-invariants.mjs`, whose probe step pipes to `tee` — without the explicit `set -o pipefail` the entire gate would have been decorative. Any `run:` block whose **exit code is the point** must open with `set -o pipefail` (or `set -euo pipefail`); `.github/workflows/preview-deploy.yml` is the in-repo reference. Piping is only safe without it when the last command in the pipe is the one whose status you actually want. Note this is a GitHub default, not a bash one — the trap does not reproduce in a local shell where you ran the same line by hand.

- **Node version: repo pins Node 22 via `.nvmrc`** — run `nvm use` to align local with CI. Mismatched Node versions cause llms.txt drift in the Integrity check
- **Node 20 support was retired (#3570), do not re-add a per-event Node matrix split.** `ci.yml`'s `test` job used to resolve `node-version` via `fromJSON(github.event_name == 'pull_request' && '[22]' || '[20,22]')` — Node 20 ran only on push-to-main/merge_group/schedule, never on the PR that introduced a change. That made Node-20-only breakage structurally invisible before merge: it landed on `main` first, every time (#3558 was exactly this). Evidence for dropping rather than adding Node 20 to PRs: `.nvmrc` was already 22, every service `Dockerfile` already pinned `node:22-alpine`, no `package.json` `engines.node` anywhere in the workspace required 20, and DO App Platform deploys those same Docker images (no separate Node-20 runtime target existed anywhere). Root `engines.node` is now `>=22`; `ci.yml`'s matrix is a flat `node-version: [22]` with no event conditional. If Node 20 (or any older major) ever needs to come back, add it to the matrix unconditionally for every trigger — a conditional that diverges by `github.event_name` reintroduces this exact blind spot
- **Architecture Audit only needs CLI deps built.** The job uses `pnpm build --filter @mbe/cli...` (turbo `...` = transitive deps). Never use bare `pnpm build` here — unrelated packages with TS errors (e.g. agent-service test files) would fail the entire job even though they have nothing to do with ADR/dep checks
- **ACMM scanner checks file/dir existence, not contents.** Criteria marked `scannable: false` (correction-capture, positive-reinforcement, session-summary, etc.) pass detection when the directory exists — even if it's empty. Always audit substance (file count, entry quality) separately when evaluating maturity level
- **Adding/changing packages regenerates the dependency graph** — CI's Build job regenerates the graph and fails if committed `infrastructure/worker/dep-graph.json` or `docs/architecture/dependency-graph.md` don't match. The pre-commit hook doesn't run this, but the `regen-dep-graph.sh` PostToolUse hook (`.claude/hooks/`) now auto-regenerates and re-stages both artifacts whenever Claude Code edits a `package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml`. For edits made outside Claude Code (or if the hook was skipped), run `pnpm graph && pnpm generate:dep-graph` manually before pushing
- **E2E workflow requires rialto built** — `@mattbutlerengineering/rialto/styles` export points to `dist/lib/styles.css` (a build artifact). Without `pnpm build --filter @mattbutlerengineering/rialto` before E2E tests, Vite can't resolve any rialto imports
- **Worktree agent PRs may target wrong base branch** — `isolation: "worktree"` agents branch from whatever commit the worktree was created at. If spawned from a feature branch, the PR targets that branch (not `main`). After agent completes, verify the PR's base ref is `main` — if not, close and recreate from a rebased branch
- **`buildApp()` cold-start exceeds 5 s vitest default on Node 20 CI** — Fastify app initialization (plugins, Prisma, JSON schema compilation) takes >5 s on a cold Node 20 runner, causing spurious `Test timed out in 5000ms` failures in route tests (broke main at 16c4426 via deposits.test.ts). Fix: set `testTimeout: 15000` in the service's `vitest.config.ts`. If you see a timeout in a route-level test on Node 20 only, check whether the service vitest config has a `testTimeout` increase.
- **Any `pnpm-lock.yaml` change forces a cold, fully parallel CI run — that's what tips marginal-timeout test suites over** — `pnpm-lock.yaml` is a turbo `globalDependencies` entry (`turbo.json`), so touching it (even a `devDependency`-only bump with zero source changes, e.g. adding `@vitest/coverage-v8`) invalidates turbo's cache for **every** task, not just the changed package. Under that cold, ~40-task-concurrent load, `tools/cli`'s `check-model subcommand` tests (`agent.test.ts`) blew past vitest's 5s default and broke `main`'s push CI at `ec35b2cf` (#3588 — see `.claude/reflections/RCA-PR-3588.md`), even though the suite passes reliably (352/352) run in isolation with workspace deps pre-built. This is the same class as the `buildApp()` bullet above, just a different trigger (lockfile cache-bust vs. Node-20-cold-runner) and a different suite. Fix pattern is identical: `testTimeout: 15000` on the affected package's `vitest.config.ts` (already applied to `tools/cli`). If a PR touches `pnpm-lock.yaml` (even indirectly, via a new `catalog:` devDependency), treat every downstream package's default-5s-timeout test suites as running under cold-cache conditions for that CI run, not the usual cached-and-fast one.
- **`revert-rca.mjs` used to fire an RCA the instant a revert PR was _proposed_, not merged (fixed in #3590)** — `revert-watchdog.yml` calls `scripts/revert-rca.mjs` immediately after _opening_ a `revert: #<N> ...` PR, before that PR can possibly be merged. The pre-#3590 script trusted a caller-supplied `--revert-sha` (the culprit's own merge commit) unconditionally, so it filed a "PR #N was reverted" issue even when the proposed revert PR was later closed without merging — conflating "proposed" with "merged". Confirmed twice: #3545/#3559 → false RCA #3560 (fixed by #3590's `classifyRevertState()` returning `none`/`proposed`/`merged`, only filing on `merged`); #3588/#3614 → issue #3615 filed at `20:15:22Z`, nine minutes _before_ #3590 merged at `20:24:07Z` — a straggler from the pre-fix window, not a recurrence. If you ever touch revert/RCA automation again, keep `findRevertPr()` + `classifyRevertState()` as the single source of truth for "was this actually reverted" — never trust a revert-sha argument passed at revert-_proposal_ time.
- **Pulumi Deploy "success" can be a skipped run** — the workflow reports `success` even when `Deploy Infrastructure` job was skipped (triggered by failed static deploy). Check the job-level conclusion, not workflow-level, to determine if Pulumi actually ran
- **DO + Pulumi dual-deploy race** — `deploy-services.yml` (doctl) and `pulumi-up.yml` both manage the same DO App Platform resource. Every `doctl apps create-deployment` triggers a paired "app spec updated" deployment that gets CANCELED. If Pulumi detects spec drift from doctl, `pulumi up` can hang waiting for DO deployment to complete

- **`GITHUB_TOKEN`-authored PRs never fire `CI Gate` — the anti-recursion trap, six rediscoveries in one week (#3538, #3572, #3566, #3584, #3625, #3623).** GitHub does not fire other workflows from events triggered by the default `GITHUB_TOKEN` (anti-recursion). A PR opened or a branch pushed by automation using `GITHUB_TOKEN` therefore never triggers `ci.yml`'s `pull_request` event — `CI Gate`, the sole required status check on `main`, never appears. The PR shows ~3 checks (CodeQL only) instead of the usual ~31, `mergeStateStatus=BLOCKED`, and nothing is red — it just silently never becomes mergeable. `workflow_dispatch` is the documented exception: it's an explicit API call, not a passive event, so it isn't subject to the anti-recursion rule. Fix: after creating the PR, dispatch CI on its branch directly, gated on a PR actually having been created (a no-op day stays a silent no-op):

  ```yaml
  permissions:
    actions: write # else the dispatch call below 403s
  steps:
    - name: Dispatch CI on the automation branch
      if: steps.create-pr.outputs.pull-request-number
      env:
        GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      run: gh workflow run ci.yml --ref automation/my-branch
  ```

  `.github/workflows/drift-fix.yml` is the in-repo reference implementation (see its "Dispatch CI on the automation branch" step); `ci.yml` carries a bare `workflow_dispatch:` trigger specifically to accept this. ## Pulumi / R2 state backend

- **A CI runner image can silently pick the version of a tool that deploys production — generalises beyond Pulumi.** Any workflow step that shells out to a tool the runner image ships preinstalled (`pulumi`, `terraform`, `aws`, `docker`, language toolchains installed via a system package manager, etc.) without an explicit version pin inherits whatever version that image happens to carry _today_. GitHub bumps runner images on its own schedule, with no changelog review from us and no correlation to any repo change — so a deploy can start failing (or, worse, silently start behaving differently) with a zero-diff push. The fix pattern is always the same: pin the tool to an explicit version in the workflow, install it explicitly rather than trusting PATH, and back the pin with a test that reads the real workflow file and asserts the pin is present and exact (not a floating range) — see `scripts/__tests__/pulumi-cli-pin.test.mjs`. Treat "the runner image updated" as a first-class root-cause hypothesis whenever a deploy workflow breaks with no corresponding repo change.
- **Concretely for Pulumi: the ubuntu24 runner image bump 20260720.247 → 20260810.271 (2026-08-11) took the preinstalled Pulumi CLI 3.253.0 → 3.256.0, and 3.256.0's S3 blob layer sends upload checksums Cloudflare R2 rejects — `InvalidDigest` on the Pulumi lock-file `PutObject`.** Production infra deploys (`pulumi-up.yml`) broke for hours with zero repo changes (#4117/#4118). Fixed short-term by pinning the CLI to 3.253.0 explicitly (`curl -fsSL https://get.pulumi.com | sh -s -- --version 3.253.0`, installed _before_ any step that shells out to `pulumi`, and every `pulumi/actions` step given the same `pulumi-version:` — its unpinned default is `^3`, which resolves to latest and reintroduces the exact float that caused the outage). The pin is deliberately a holding action, not a permanent fix — it freezes the CLI while `@pulumi/pulumi` (the Node SDK `infrastructure/pulumi` actually imports) keeps moving forward, so the gap only grows with every future SDK bump.
- **The likely real fix — newer AWS SDKs enable request checksums (CRC32) by default on upload operations, and R2 has documented incompatibilities with that default; Cloudflare's workaround is `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` / `AWS_RESPONSE_CHECKSUM_VALIDATION=when_required` set at JOB level — is untested against this repo's real backend as of #4119.** It was deliberately NOT applied directly to `pulumi-up.yml` in #4118: that workflow only runs on push to `main`, so the first real exercise of an untested env var would have been against production Pulumi state, on an already-red main. `.github/workflows/pulumi-r2-checksum-validation.yml` (#4119) is a `workflow_dispatch`-only harness that validates the fix empirically against a **scratch** R2 bucket instead — never production state. `scripts/pulumi-r2-validation-guard.mjs`'s `assertScratchBucketSafe` is the load-bearing guard: it parses the real production bucket name straight out of `pulumi-up.yml`'s own `s3://` cloud-url (never hardcoded separately, so a bucket rename there can't silently desync the guard) and hard-fails on a blank bucket, a missing bucket, or any case-/whitespace-variant of the production name. Do not raise or remove the `pulumi-up.yml` pin based on running this harness only in your head — it must actually be dispatched and its verdict read before that follow-up is safe.
- Note: the upstream issue found while diagnosing this (pulumi/pulumi#23478) is a _different_ symptom (`CopyObject` / `InvalidArgument`) from ours (`PutObject` / `InvalidDigest`) — don't assume a fix for one covers the other.

## Fastify / rate limiting

- **Declaring a route-level `config.rateLimit` REPLACES the service-wide limiter for that route — move its `hook` and the route's unauthenticated surface silently loses every bound (#4492 → fixed #4499).** `@mbe/service-bootstrap`'s `createServiceApp` registers `@fastify/rate-limit` globally (100/min, default `onRequest`). A route that declares its own `config.rateLimit` opts out of that one; the plugin's `onRoute` hook takes the `else if (globalParams.global)` branch only when `config.rateLimit == null`. Normally harmless, because every other route in this repo keeps the default `onRequest` timing — it swaps one limiter for an equivalent-or-stricter one at the same stage. `POST /api/v1/venues` set `hook: "preHandler"` so the cap could key on the verified `sub` (correct — `request.user` does not exist at `onRequest`, and IP-keying lets one office NAT lock out everyone behind it). The consequence was that body-schema validation's 400 and `requireAuth`'s 401 both answer _before_ the limiter, leaving a publicly reachable POST with no bound at all. Nothing went red: an absent limiter and a present one are identical to lint, typecheck, and every single-request test. **Detection is a live probe, not a diff** — `GET /api/v1/venues` answers 401 carrying `x-ratelimit-limit: 100`; the `POST` on the same path carried no rate-limit headers on either its 400 or its 401. Diff response headers against a sibling route on the deployed service.
- **You cannot fix this with a second rate-limit hook — `@fastify/rate-limit` runs at most ONE limiter per request.** `rateLimitRequestHandler` sets a `rateLimitRan` flag on the request and every later limiter short-circuits to `next()` (`index.js:319-327`, v11.2.0), so `onRequest: fastify.rateLimit(a)` + `preHandler: fastify.rateLimit(b)` silently applies only `a`. The escape hatch is `fastify.createRateLimit(opts)`, which returns `(req) => Promise<result>` calling `applyRateLimit` directly and never touches that flag. Pattern that works: declare **no** `config.rateLimit` (so the global `onRequest` limiter keeps covering the anonymous surface) and enforce the per-identity cap by hand in a preHandler after `requireAuth`, replying 429 on `isExceeded`. Narrow on `result.isAllowed` first — the return is a discriminated union and the allow-list branch carries no counters.

- **Prisma generated clients are NOT committed** — `services/*/src/generated/` is gitignored. Clients are produced by `prisma generate` via each service's `postinstall` script (runs automatically on `pnpm install --frozen-lockfile`).
