# Known gotchas

Project-specific traps that have bitten me before. Read these before diving into pre-commit, release, or deploy work.

> **Adding entries:** after an autonomous loop (`/implement-queue`, `/ship-loop`), run `/gotcha-harvest` to mine the session for `CI failed → fix → passed` arcs and recurring tool-errors — it proposes new bullets here (and cross-repo facts to memory) with human review. `/reflect` only captures _human corrections_, so loop-discovered gotchas land here via `/gotcha-harvest`, not `/reflect`.

## Pre-commit / lint

- **There is no `$CLAUDE_FILE_PATH` — hooks get the edited path as JSON on stdin (fixed in #3631).** Measured against the installed binary (v2.1.220): the string `CLAUDE_FILE_PATH` does not occur in it at all, and the only hook-injected env var is `CLAUDE_PROJECT_DIR`. The path arrives on **stdin** as `{"hook_event_name":…,"tool_name":"Write","tool_input":{"file_path":"/abs/path"},"tool_use_id":…}`. Seven hooks in `.claude/settings.json` used to interpolate the nonexistent variable, which expanded to `""` — so `prettier --write ""` recursively reformatted the **entire working directory** (168 tracked files, silenced by `2>/dev/null`) and `case "" in *.env|*pnpm-lock.yaml|…)` matched nothing, leaving the `.env`/lockfile/migration/`Pulumi.prod.yaml` guard inert for its whole life. Every path-aware hook now starts with `FILE=$(node "$CLAUDE_PROJECT_DIR/.claude/hooks/hook-input.mjs"); [ -n "$FILE" ] || exit 0;`. **Never pass an unguarded variable to a formatter** — an empty argument means "everything" to `prettier`, `eslint`, and most CLI tools, so the `-n` guard stays even now that the path resolves. `settings.json` is strict JSON (no comments), so the contract is documented in `scripts/hook-input.mjs` — the one module that owns "how does a hook obtain its input" — and enforced by `scripts/__tests__/hook-input.test.mjs`, which executes every real hook command in a sandbox. `CLAUDE_BASH_COMMAND`, `CLAUDE_TOOL_INPUT` and `CLAUDE_TOOL_OUTPUT` are **also** absent from the binary, so `pre-bash-guard.sh`, `pre-push-typecheck.sh`, `verify-push-sha.sh` and `regen-after-update-branch.sh` are inert for the same reason (tracked separately). They can adopt the adapter unchanged via `extractHookField(payload, "command")` — but **review `regen-after-update-branch.sh` lines 36-58 before repairing its input**: it runs `git checkout origin/$branch --detach` and `git push --no-verify` in the live working tree and has never once executed.
- **PreToolUse secret-scan hook (`.claude/hooks/secret-scan.mjs`)** shifts the CI Gitleaks scan left to edit time: on `Edit|Write|MultiEdit` it scans the content an agent is about to write for high-confidence secrets (Stripe `sk_live_`/`pk_live_`/`rk_live_`, AWS `AKIA`/`ASIA` key ids, JWTs, PEM private-key headers) and **blocks the write (`exit 2`)** on a hit, before the secret ever reaches a commit. Detection is the pure, unit-tested `scanForSecrets()` in `scripts/secret-scan.mjs` (test-mode keys, `.example`/`.sample`, `__tests__`/`fixtures`, and `.md` are allowlisted to keep false positives near zero); the hook fails **open** (`exit 0` on any parse error) so a hook bug never deadlocks editing. The hook is wired in `.claude/settings.json` under `PreToolUse`.
- Pre-commit hook runs `eslint --fix` + `check-adr` + `pack-changed` (the last one regenerates `llms.txt` / `llms-full.txt` in affected packages — expect them to appear in `git status` after your commit lands)
- JSX strings with `'` fail `react/no-unescaped-entities` at commit time — use `&apos;`
- **Rialto components must NOT call `setState` inside a `useEffect` body** (pre-commit hook bans it in `packages/rialto`). Setting state re-renders → re-runs the effect → sets state again = render loop. Use render-time derivation (compute during render, the snapshot pattern) or event handlers (set state only on user actions). LLMs default to the forbidden useEffect+setState sync pattern from general React tutorials — it's a correctness bug in Rialto's rendering model
- **lint-staged passes generated files to ESLint as explicit CLI args** — ESLint 10's `ignores` array in config only applies to glob-resolved files, not explicit paths. When lint-staged stages a Prisma generated file (`services/*/src/generated/**`), it passes the path directly to `eslint`, bypassing the ignore. `lint-staged.config.js` filters `/generated/` paths before grouping to prevent this

## Pre-push / typecheck

- **Vitest does NOT typecheck** — tests can pass with completely wrong types. Pre-push hook now runs `turbo typecheck` before `turbo test`. If you add test mocks, they must match the actual interface shape (e.g. `SessionResult` needs `status`/`sessionId`/`branchName`, not `success`/`stuck`/`outputs`)
- **Worktree agents must run `pnpm typecheck` before declaring done.** Agents that only run `pnpm test` will miss type errors that break CI. This is the #2 recurring CI failure pattern after the missing `pnpm install` pattern

## Build / pnpm / turbo

- Run `pnpm` from inside a package directory, not the monorepo root — turbo filter errors out at the root for `test`/`typecheck`/`build` in most packages
- Parallel `Bash` tool calls don't share `cd` state and race each other — use absolute paths or `pnpm --dir <abs-path> <cmd>` when running in parallel
- **Worktree agents must `pnpm install --frozen-lockfile` before running tests/builds.** Claude Code `isolation: "worktree"` creates a bare checkout without `node_modules`. Without the install step, `vitest: command not found` / `ELIFECYCLE` failures are guaranteed. This is the #1 recurring CI failure pattern across agent sessions
- **`gh pr update-branch` drifts llms.txt artifacts** — the merge brings in new main changes but doesn't re-run `pnpm regen`. CI's "Verify generated artifacts" step then fails on stale llms.txt/llms-full.txt. The `regen-after-update-branch.sh` PostToolUse hook auto-fixes this by building the CLI (`pnpm build --filter @mbe/cli...`), running `pnpm regen`, and pushing a fixup commit. If the hook is unavailable, run manually: `pnpm build --filter @mbe/cli... && pnpm regen`, then commit and push
- **llms-drift treadmill (fixed in #2745)** — three root causes caused every worktree-PR to need a manual regen cycle: (1) `@mbe/agent-core/dist` is absent in fresh worktrees → `mbe pack` fails with `ERR_MODULE_NOT_FOUND` → llms NOT rebuilt; (2) `regen.mjs` ran `llms-txt` BEFORE `rialto-catalog-schemas` → llms embedded the pre-regen schema while CI regenerated with the post-regen schema; (3) the update-branch hook didn't build the CLI before regen → hook was a no-op. All three are now fixed: pre-push builds CLI first, `regen.mjs` runs llms-txt last, and the update-branch hook also builds CLI. Residual caveat: if `pnpm build --filter @mbe/cli...` fails (e.g. TS error introduced by the PR), the pre-push hook aborts before regen — fix the build error first
- **llms regen also requires `packages/agent-core` built, and the PostToolUse hook fails open on it** — `mbe pack <pkgDir>` (the `@mbe/cli` command the llms-txt family's `changedBy()` shells out to) imports `@mbe/agent-core`, so a maximally-fresh worktree missing `packages/agent-core/dist` throws `ERR_MODULE_NOT_FOUND`, not just a missing CLI build. `regen-llms.sh` runs that command with `"${cmd_arr[@]}" >/dev/null 2>&1 || continue` — the failure is silently swallowed (no warning printed, loop just moves to the next family), so the hook no-ops with zero signal. Always `pnpm build --filter @mbe/cli...` (which builds `agent-core` as a transitive dep) before relying on the hook or running `mbe pack`/`pnpm regen` by hand
- **`infrastructure/worker` is not a pnpm workspace package** — `pnpm-workspace.yaml` only lists `infrastructure/pulumi` under `infrastructure/*`, and the directory has no `package.json`. Its `*.test.js` files (edge-router, health, rate-limiter, csp, etc.) are invisible to `pnpm lint`/`turbo lint`, `pnpm test`/`turbo test`, the root `vitest.config.ts` workspace globs, and `CI Gate` — a change there can be green in CI while its own tests never ran. Run them directly: `pnpm exec vitest run infrastructure/worker/`
- **`pnpm exec mbe <cmd>` fails with `Command "mbe" not found`** — the `@mbe/cli` bin (`tools/cli/package.json`'s `bin.mbe`) is never linked into any `node_modules/.bin`: pnpm only symlinks a workspace package's bin into consumers that declare it as a `dependency`, and nothing in the workspace depends on `@mbe/cli`, so `pnpm exec` fails even run from inside `tools/cli` itself. After `pnpm build --filter @mbe/cli...`, invoke `node tools/cli/dist/index.js <cmd>` or `pnpm --filter @mbe/cli start <cmd>` instead. `claude.yml`'s `pnpm exec mbe agent run` step shares this bug.

## CI

- **GH Actions is paid and runs on every PR** — verify state with `gh run list --limit 5` before claiming CI is broken
- **Green-main policy: main must always be green.** No admin-merge through red checks. If main breaks, fix is top priority. Emergency revert is the only exception
- **`CI Gate` is the only _required_ status check on `main`.** `codecov/patch` (patch-coverage delta) and `Hospitality E2E` (auth/booking-widget specs, frequently red for environmental/auth-bypass reasons) are advisory — not required. Gate merge decisions on `CI Gate` + the build/test/lint/typecheck/Integrity/Architecture-Audit jobs, not on an all-green rollup. Verify required contexts with `gh api repos/.../branches/main/protection/required_status_checks`. `main` is `strict` (requires up-to-date branches before merge)
- **Auto-merge, not merge queue (personal-account repo).** GitHub's native merge queue (`merge_queue` ruleset rule, the dormant `merge_group:` trigger in `ci.yml`) is **org-repos-only** — creating the ruleset on this personal-account repo returns `422 Invalid rule 'merge_queue'`. The implement-queue merge train uses **auto-merge** instead: `gh pr merge <N> --auto --squash --delete-branch` (repo has `allow_auto_merge: true`). `--auto` enqueues the merge; GitHub completes it once `CI Gate` is green **and** the branch is up to date — it does **not** auto-rebase. Because `main` is `strict`, a PR that falls behind after a sibling merges silently won't auto-merge until re-`update-branch`ed (the loop's next iteration handles this). To dequeue, `gh pr merge <N> --disable-auto`. Run the diff-matched review gate **before** setting `--auto` — once enqueued, GitHub merges on green with no further human gate
- **Node version: repo pins Node 22 via `.nvmrc`** — run `nvm use` to align local with CI. Mismatched Node versions cause llms.txt drift in the Integrity check
- **Node 20 support was retired (#3570), do not re-add a per-event Node matrix split.** `ci.yml`'s `test` job used to resolve `node-version` via `fromJSON(github.event_name == 'pull_request' && '[22]' || '[20,22]')` — Node 20 ran only on push-to-main/merge_group/schedule, never on the PR that introduced a change. That made Node-20-only breakage structurally invisible before merge: it landed on `main` first, every time (#3558 was exactly this). Evidence for dropping rather than adding Node 20 to PRs: `.nvmrc` was already 22, every service `Dockerfile` already pinned `node:22-alpine`, no `package.json` `engines.node` anywhere in the workspace required 20, and DO App Platform deploys those same Docker images (no separate Node-20 runtime target existed anywhere). Root `engines.node` is now `>=22`; `ci.yml`'s matrix is a flat `node-version: [22]` with no event conditional. If Node 20 (or any older major) ever needs to come back, add it to the matrix unconditionally for every trigger — a conditional that diverges by `github.event_name` reintroduces this exact blind spot
- **Architecture Audit only needs CLI deps built.** The job uses `pnpm build --filter @mbe/cli...` (turbo `...` = transitive deps). Never use bare `pnpm build` here — unrelated packages with TS errors (e.g. agent-service test files) would fail the entire job even though they have nothing to do with ADR/dep checks
- **ACMM scanner checks file/dir existence, not contents.** Criteria marked `scannable: false` (correction-capture, positive-reinforcement, session-summary, etc.) pass detection when the directory exists — even if it's empty. Always audit substance (file count, entry quality) separately when evaluating maturity level
- **Adding/changing packages regenerates the dependency graph** — CI's Build job regenerates the graph and fails if committed `infrastructure/worker/dep-graph.json` or `docs/architecture/dependency-graph.md` don't match. The pre-commit hook doesn't run this, but the `regen-dep-graph.sh` PostToolUse hook (`.claude/hooks/`) now auto-regenerates and re-stages both artifacts whenever Claude Code edits a `package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml`. For edits made outside Claude Code (or if the hook was skipped), run `pnpm graph && pnpm generate:dep-graph` manually before pushing
- **E2E workflow requires rialto built** — `@mattbutlerengineering/rialto/styles` export points to `dist/lib/styles.css` (a build artifact). Without `pnpm build --filter @mattbutlerengineering/rialto` before E2E tests, Vite can't resolve any rialto imports
- **Worktree agent PRs may target wrong base branch** — `isolation: "worktree"` agents branch from whatever commit the worktree was created at. If spawned from a feature branch, the PR targets that branch (not `main`). After agent completes, verify the PR's base ref is `main` — if not, close and recreate from a rebased branch
- **`buildApp()` cold-start exceeds 5 s vitest default on Node 20 CI** — Fastify app initialization (plugins, Prisma, JSON schema compilation) takes >5 s on a cold Node 20 runner, causing spurious `Test timed out in 5000ms` failures in route tests (broke main at 16c4426 via deposits.test.ts). Fix: set `testTimeout: 15000` in the service's `vitest.config.ts`. If you see a timeout in a route-level test on Node 20 only, check whether the service vitest config has a `testTimeout` increase.
- **Any `pnpm-lock.yaml` change forces a cold, fully parallel CI run — that's what tips marginal-timeout test suites over** — `pnpm-lock.yaml` is a turbo `globalDependencies` entry (`turbo.json`), so touching it (even a `devDependency`-only bump with zero source changes, e.g. adding `@vitest/coverage-v8`) invalidates turbo's cache for **every** task, not just the changed package. Under that cold, ~40-task-concurrent load, `tools/cli`'s `check-model subcommand` tests (`agent.test.ts`) blew past vitest's 5s default and broke `main`'s push CI at `ec35b2cf` (#3588 — see `.claude/reflections/RCA-PR-3588.md`), even though the suite passes reliably (352/352) run in isolation with workspace deps pre-built. This is the same class as the `buildApp()` bullet above, just a different trigger (lockfile cache-bust vs. Node-20-cold-runner) and a different suite. Fix pattern is identical: `testTimeout: 15000` on the affected package's `vitest.config.ts` (already applied to `tools/cli`). If a PR touches `pnpm-lock.yaml` (even indirectly, via a new `catalog:` devDependency), treat every downstream package's default-5s-timeout test suites as running under cold-cache conditions for that CI run, not the usual cached-and-fast one.
- **`revert-rca.mjs` used to fire an RCA the instant a revert PR was _proposed_, not merged (fixed in #3590)** — `revert-watchdog.yml` calls `scripts/revert-rca.mjs` immediately after _opening_ a `revert: #<N> ...` PR, before that PR can possibly be merged. The pre-#3590 script trusted a caller-supplied `--revert-sha` (the culprit's own merge commit) unconditionally, so it filed a "PR #N was reverted" issue even when the proposed revert PR was later closed without merging — conflating "proposed" with "merged". Confirmed twice: #3545/#3559 → false RCA #3560 (fixed by #3590's `classifyRevertState()` returning `none`/`proposed`/`merged`, only filing on `merged`); #3588/#3614 → issue #3615 filed at `20:15:22Z`, nine minutes _before_ #3590 merged at `20:24:07Z` — a straggler from the pre-fix window, not a recurrence. If you ever touch revert/RCA automation again, keep `findRevertPr()` + `classifyRevertState()` as the single source of truth for "was this actually reverted" — never trust a revert-sha argument passed at revert-_proposal_ time.
- **Pulumi Deploy "success" can be a skipped run** — the workflow reports `success` even when `Deploy Infrastructure` job was skipped (triggered by failed static deploy). Check the job-level conclusion, not workflow-level, to determine if Pulumi actually ran
- **DO + Pulumi dual-deploy race** — `deploy-services.yml` (doctl) and `pulumi-up.yml` both manage the same DO App Platform resource. Every `doctl apps create-deployment` triggers a paired "app spec updated" deployment that gets CANCELED. If Pulumi detects spec drift from doctl, `pulumi up` can hang waiting for DO deployment to complete

- **pnpm-lock.yaml quote style diffs are formatting noise** — different pnpm versions use single vs double quotes for keys. These are not real changes. Revert with `git checkout -- pnpm-lock.yaml` rather than committing formatting-only lockfile diffs

- **Local `generated-schemas.ts` modifications pollute drift-check** — if `packages/rialto-catalog/src/generated-schemas.ts` has uncommitted changes (e.g. from running the generator with different rialto dist), the drift-check test reads the modified file and fails. Fix: `git checkout -- packages/rialto-catalog/src/generated-schemas.ts` before push

- **New packages with committed llms files must be added to `regen-manifest.mjs`** — every git-tracked `llms.txt`/`llms-full.txt` must have a corresponding entry in the `FAMILIES` array in `scripts/regen-manifest.mjs`. When a new package under `packages/` adds those files without a manifest entry, the CI coverage test ("every git-tracked llms.txt/llms-full.txt file has a manifest entry") fails. Add both outputs to `FAMILIES` in alphabetical order by package path before pushing.

- **Rialto-web visual baselines are Linux CI runner-specific — regenerate from CI artifact, not macOS** — Playwright screenshots differ between macOS and Linux due to font-metric/glyph-advance differences. When baselines need updating, pull `*-actual.png` files from the `rialto-web-visual-diffs` CI artifact (any Linux run on the PR's base commit); never commit baselines rendered locally on macOS. Actuals are byte-identical across CI retries so any single Linux run at the same base commit is authoritative.

- **Changing a shared Heading/CSS primitive's `line-height` cascades ±1px visual failures in non-adjacent sections** — at `1.2rem` (19.2 px) a 0.3-unit leading change shifts each line-box by 5.76 px; the fractional upstream layout shift changes device-pixel rounding of every section below the changed component on the visual-test harness page. Sections with no code relationship to the change can flip ±1 px. Expect 18+ failing baselines; regenerate from CI artifact after landing the CSS change. Merging a PR with its own visual CI red starts a cascading red streak on main affecting all subsequent PRs.

## Dependencies

- **pnpm.overrides for CVEs: use the scoped pattern** `"pkg@<patched": "^patched"`, not `"pkg": ">=patched"` — the open range resolves to the latest satisfying version and can pull major bumps (e.g. `protobufjs@>=7.5.5` → 8.0.1)
- **Broad js-yaml CVE range override breaks `@changesets/cli` `safeLoad`** — the `"js-yaml@<4.2.0": "^4.2.0"` override force-upgrades `read-yaml-file@1.1.0` (pulled by `@changesets/cli`) to js-yaml@4, which stubs `yaml.safeLoad` as a throw (`Function yaml.safeLoad is removed in js-yaml 4`). This crashes `changeset version` whenever a pending changeset is present. Fix: add a consumer-path override alongside the range override — `"read-yaml-file>js-yaml": "3.14.1"`. Consumer-path overrides take precedence over range overrides in pnpm 9, so `read-yaml-file` gets js-yaml@3 while all other consumers keep js-yaml@4.
- **Zod 4 `z.record()` requires 2 args** — `z.record(z.unknown())` fails; use `z.record(z.string(), z.unknown())`. Zod 3 accepted 1 arg, Zod 4 does not
- **AI SDK v6 API renames** — `streamText` uses `stopWhen: stepCountIs(N)` (not `maxSteps`), `tool()` uses `inputSchema` (not `parameters`), fullStream text-delta events have `.text` (not `.textDelta`), and tool-call events have `.input` (not `.args`). The old names don't exist — TypeScript will catch it but only at typecheck, not at test time
- **Build job's `pnpm audit --audit-level=high` (run via `pnpm repo-audit`) can red main from a newly-published transitive CVE with zero code change** — the advisory database updates live, so a PR that never touched the flagged dependency can still fail on push. Fix with a scoped `pnpm.overrides` entry (see above); when a parent package pins an unpatchable major and no override is possible, use `pnpm.auditConfig.ignoreGhsas: ["GHSA-xxxx-xxxx-xxxx"]` in `package.json` alongside a tracking issue for the real fix.

## Releases (changesets / rialto)

- **Changesets require `GITHUB_TOKEN`**: run `GITHUB_TOKEN=$(gh auth token) pnpm version-packages` — without it, `@changesets/get-github-info` errors asking for a PAT
- **Changesets post-version prettier step errors with `Cannot find package '@mbe/config'`** — version bump + `.changeset/*.md` consumption succeed, but `packages/rialto/CHANGELOG.md` write is **silently skipped**. Manually prepend the new version block to `CHANGELOG.md` before committing the release
- **`pnpm release` regenerates `packages/rialto/package.json` exports map** when a new component folder was added — run `git status` after release and commit the follow-up diff. Otherwise the subpath `import from "@mattbutlerengineering/rialto/<NewComponent>"` works for registry consumers but is missing from the repo
- **Rialto library build fails when a component imports an un-externalized workspace package** — `vite.config.lib.ts` `rollupOptions.external` lists only `react`, `react-dom`, `react/jsx-runtime`, `framer-motion`, `lucide-react`. Any rialto component that imports a workspace sub-path (e.g. `@mbe/api-client/streaming` in `ChatPanel/useChatStream.ts`) fails the Release build with `Rolldown failed to resolve import "@mbe/…"`. Fix: add the workspace package or sub-path to `rollupOptions.external` in `vite.config.lib.ts` before merging the component.

## Tooling artifacts

- **`graphify-out/` is gitignored** (`graphify-out/` + `graphify-out-*/`) — graphify's graph/report/cache artifacts won't pollute `git status`. The skill is vendored at `.claude/skills/graphify/SKILL.md` and self-bootstraps the `graphifyy` package on first run; if invoked from a package subdir, the `graphify-out/` lands there and is still ignored by the root pattern

## Auth0 / E2E

- **Auth0 ROPC grant requires SPA or Regular Web Application** — Machine to Machine (M2M) apps return `401 access_denied` even with Password grant enabled. The `E2E_AUTH0_CLIENT_ID` must point to a SPA or Regular Web App, not M2M. Current E2E client: `mattbutlerengineering-hospitality` (SPA)
- **`gh secret set` without `--body` sets empty value** — when stdin is empty (non-interactive), the secret silently gets set to `""`. Always use `gh secret set NAME --body "value"`. An empty `E2E_AUTH0_CLIENT_ID` causes "Missing required E2E auth env vars" instead of the expected auth error

## Prisma + DO migrate

- **Prisma generated clients are NOT committed** — `services/*/src/generated/` is gitignored. Clients are produced by `prisma generate` via each service's `postinstall` script (runs automatically on `pnpm install --frozen-lockfile`). CI's `prepare` job also runs generate and caches the output for downstream jobs (typecheck, build). Never commit files under `services/*/src/generated/` — `git rm -r --cached` them if they slip in.
- **Migrate Dockerfile must pin same Prisma major as `@prisma/client`** (`infrastructure/migrate/Dockerfile`). Prisma 7 dropped schema-level `url`; client gen rejects it (P1012) while Prisma 6 CLI requires it. No schema syntax bridges both — keep them in sync. Migrate URL comes from per-service `prisma.config.ts` on Prisma 7
- **Prisma 7 `prisma.config.ts` in containers needs `ENV NODE_PATH=/usr/local/lib/node_modules`** when prisma is globally installed via `npm install -g prisma@7`. Without it the config loader fails with `Cannot find module 'prisma/config'` from any service dir
- **Verify prod DB connectivity via `/api/v1/users/health`, not `/health`** — `/health` is liveness only (returns 200 even when DB is dead); `/api/v1/users/health` runs `prisma.$queryRaw` and reports `degraded` with the actual DB error
