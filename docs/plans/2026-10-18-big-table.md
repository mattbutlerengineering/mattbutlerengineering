# The Big Table — feasibility check + build plan

> **Status: future plan — unblocked, not yet filed.** Needs no venue history, no LLM key, and no new external accounts (Stripe is already integrated). Nothing here is filed as an issue; run `/decompose` on this file to start it. File references verified against `main` at `482ed0bc6`, 2026-10-18.

## Context

Today a guest who picks a party larger than the venue's max hits a **dead end**: the widget offers a `{{max}}+` option and then says "For parties larger than {{max}}, call us" (`apps/hospitality/src/components/booking-widget/DatePartySelector.tsx`, i18n keys `bookingWidget.dateParty.largePartyCall` / `largePartyContact`). Group dinners and private events are among the highest-value bookings an independent restaurant takes, and they run on phone tag and emailed PDFs.

The Big Table turns the dead end into a visual proposal flow:

1. **Guest requests** in the widget — party size, date, occasion, budget band, notes.
2. **Owner builds a proposal** on the floor plan — drags tables together into one long table or claims an area; live seat count; sets minimum spend / per-head price and deposit.
3. **Guest gets a proposal link** — their own table arrangement on the venue's floor plan (3D if The Room in 3D, #7057, exists), the terms, and "Accept & pay deposit".
4. **On accept**, the combined tables are blocked on the timeline for that night.

Matt loved it (2026-10-18). Brand Match (#7048) styles the proposal, The Invitation (#7053) sends it to the group, Section Painter (#7059) assigns the event to a server.

## The hard decision: how a booking holds several tables

Two options; pick in the architect stage, not here:

- **A. Linked reservations** — one reservation per table, grouped by an `eventId`. No change to the availability engine (each table is just booked); risk is partial states (some tables booked, some not) — create all in one transaction with every per-table lock taken in a stable order.
- **B. Table set on one reservation** — a `ReservationTable` join table. Cleaner model, but every availability, hold, timeline and floor query that assumes one `tableId` must change.

Recommendation going in: **A**, because it leaves the riskiest code (availability) untouched. Either way, a **property test** must prove a blocked table is never offered by `generateTimeSlots` or the hold path.

## Approach

### 1. Models (additive migration, `migration-reviewer`)

- `EventRequest { id, venueId, partySize, date, occasion, budgetBand?, notes?, contactName, contactEmail, contactPhone?, status: NEW | PROPOSED | ACCEPTED | DECLINED | EXPIRED, createdAt }`.
- `EventProposal { id, requestId, tableIds String[], arrangement Json, pricing { kind: MIN_SPEND | PER_HEAD, amountCents }, depositCents, expiresAt, tokenHash, status }` — integer cents only.

### 2. Widget request form

When party size exceeds `maxPartySize`, replace the dead-end copy with a short request form (the venue phone stays as a secondary link). Public route `POST /public/v1/venues/:slug/event-requests`, per-IP rate limit, zod validation, honeypot field. Owner notified by email via the existing notifier.

### 3. Owner proposal builder

Dashboard "Events" inbox → open a request → a **copy** of the active floor plan where tables snap together (arrangement stored on the proposal; the real layout is never moved). Live seat count vs party size, pricing + deposit inputs, expiry date, preview.

### 4. Public proposal page `/p/:token`

Opaque random token (hashed at rest, revocable). Renders the arrangement read-only (`FloorPlanCanvas readOnly`), occasion, date, pricing terms, cancellation terms, and **Accept & pay deposit** through the existing Stripe deposit flow. Shows only what the guest submitted — never other bookings.

### 5. Accept → block the tables

On successful payment (webhook-confirmed, idempotent), create the multi-table booking per the chosen design, taking every table lock in a stable order; if any table was taken meanwhile, refund automatically and tell the owner. Timeline shows the event as one grouped block.

### 6. Lifecycle

Expiry reminders to the owner, declined/expired states, cancellation per the proposal's terms.

## Risks

- **Availability correctness** with multi-table bookings → design A + property test; this is the gate.
- **Payments** on larger amounts → `stripe-flow-reviewer`, webhook signature verification, idempotency keys, refund path tested.
- **Spam requests** on a public form → rate limit, honeypot, validation; requests never block inventory until accepted.
- **Scope** → steps 1–2 alone (capture requests instead of a dead end) are shippable and valuable.

## Verification

- Unit: proposal pricing (integer cents), arrangement seat count, token hashing, expiry.
- Property: tables in an accepted event are never returned by `generateTimeSlots` or accepted by `holdService.create` for overlapping times.
- Route: request rate limit 429; proposal page 404 for bad token, 410 for expired; payment webhook replay is idempotent; race on accept → refund path.
- E2E (hospitality Playwright): party of 14 → request form → owner builds a 3-table arrangement → guest opens link → accept with Stripe test card → timeline shows the grouped block and the tables are unbookable.
