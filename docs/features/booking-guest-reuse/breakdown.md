## Design gaps found

**G1 — `GuestLookup` listbox entrance depends on `framer-motion`, which `apps/hospitality` does not have, and on a static motion-token import ADR-025 supersedes.** Routed to Architect; nothing was designed around it. **Resolved 2026-09-15** — see the last bullet.

- What the architecture says: § `GuestLookup` renders the portaled list as `motion.ul` with `initial`/`exit` gated by `useReducedMotion` and a `precision` transition; § Stack names "framer-motion `useReducedMotion` + rialto's `precision` preset for the listbox entrance (ADR-025 motion through presets)" and, in the same section, "no new runtime dependency". Collaborators: "framer-motion (`useReducedMotion`, `precision` from rialto — as `Autocomplete.tsx` imports it)".
- What the repo says: `apps/hospitality/package.json` has no `framer-motion` dependency (direct or dev) and `require.resolve("framer-motion", { paths: ["./apps/hospitality"] })` throws `MODULE_NOT_FOUND`; `.npmrc` has only `auto-install-peers=true`, and rialto lists framer-motion as its own dependency, not a peer, so nothing hoists it into the app's resolution. `Autocomplete.tsx` is a rialto component: it imports `framer-motion` and `../../tokens/motion` from inside `packages/rialto`, which is not a path an app can copy. The `@mattbutlerengineering/rialto/motion` subpath (`dist/lib/motion.js`) exports tokens only (`precision`, `spring`, …) and `@mattbutlerengineering/rialto/hooks` exports no reduced-motion hook. ADR-025 (active, "Components ask the environment for their motion config instead of importing a constant") supplies `useMotionPreset()` via `@mattbutlerengineering/rialto/providers` — it returns a `MotionPreset`, collapses to instant under reduced motion and never throws — and treats a static `precision` import in a component as the pattern it retired.
- Why Decompose cannot close it: the three ways out are design choices with different blast radii — (1) add `framer-motion` as a direct `apps/hospitality` dependency (contradicts "no new runtime dependency"; `pnpm-lock.yaml` change → cold fully-parallel CI run per gotchas; dep-graph regen; size-limit 500 kB JS check — framer is already in the vendor chunk via rialto, so the delta may be small, but that is a measurement Architect owns); (2) render the listbox with no framer entrance (CSS-only or none; SC14's reduced-motion clause holds trivially; changes the UX's stated entrance); (3) have rialto export a motion-aware listbox/entrance primitive (rialto change + changeset + build, widens the run into the design system). Each also decides whether `useMotionPreset()` (ADR-025) or `useReducedMotion` (architecture text) is the gate. Picking one here would be designing around a stated constraint.
- Blast radius: M2.6 only, plus SC14's reduced-motion clause and M6.5's lockfile/size expectations. M1, M2.1–M2.5, M2.7, M5 are unaffected and can proceed; M2.8, M3, M4, M6.1–M6.3 wait on M2.6.
- Resolution (2026-09-15, Architect re-entry, unattended): **option (2), CSS-only entrance.** `GuestLookup.module.css` declares one `@keyframes` (fade + 4 px rise) on the listbox class over `var(--rialto-duration-standard) var(--rialto-ease-precision)` — the exact values `precision` carries (0.15 s, `cubic-bezier(0.2, 0, 0, 1)`) — and `animation: none` under `@media (prefers-reduced-motion: reduce)`; no exit animation. Gate: the media query, no hook. Import path: none — no `framer-motion` and no `useMotionPreset()` in `GuestLookup.tsx`. `pnpm-lock.yaml`: **does not change.** Correction to the record above: rialto declares `framer-motion` as a `peerDependencies` entry (`^12.0.0 || ^13.0.0`) plus a `devDependencies` entry, not a `dependencies` one; the conclusion holds (it does not resolve from `apps/hospitality`, and `apps/marketing`/`apps/rialto-web` carry it directly, so option (1) would have been a lockfile importer change). Why (1) and (3) lost is in architecture.md § Decisions & alternatives. M2.6's AC gains the grep-pinned motion clause; its blockers are now M2.3, M2.5.
